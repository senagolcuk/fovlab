# 04 — UI and interaction

## Screen layout

```
┌──────────────────────────────────────────────────────────────┐
│  app bar — title, coordinate frame hint, zoom, fit           │
├────────────────┬─────────────────────────────────────────────┤
│                │                     │                       │
│  sidebar       │        TOP          │        FRONT          │
│  360 px        │                     │                       │
│  scrollable    ├─────────────────────┼───────────────────────┤
│                │                     │                       │
│                │        LEFT         │        ISO            │
│                │                     │        (orbit, drag)  │
└────────────────┴─────────────────────┴───────────────────────┘
```

Desktop only, minimum 1280 px. Below that, show a message rather than a broken layout.

Light theme. Two faces, split by whether the type is a word or a figure:

- **Prompt** for the interface. The wordmark, panel headings, control captions, field labels,
  helper text, buttons, dialogue copy. It is the theme's default, so nothing has to ask for it.
- **Roboto Mono** for every number an engineer will read off the screen — the value inside a
  field, coordinates, angles, areas, the pane scales. Numbers in a proportional face are hard to
  compare down a column.

Roboto stays in the stack behind Prompt as the fallback, and nowhere else. Nothing is set in one
face rather than the other to make it louder — weight and colour do that.

### Palette

Six colours, in `PALETTE` in `theme.ts`. Anything added later picks from these rather than
inventing a neighbouring shade.

| Token | Hex | Used for |
|---|---|---|
| `blue` | `#1E79D3` | primary — actions, links, the nose marker |
| `slate` | `#495F81` | secondary — panel titles, secondary text, vehicle edges |
| `sky` | `#B0CED7` | selected rows, panel header tint |
| `orange` | `#FFA52C` | warnings, the `Unverified` chip |
| `offWhite` | `#F1F1F1` | sidebar background, behind the cards |
| `grey` | `#BFBFBF` | dividers and card borders |

Orange carries **dark** text: white on it is about 1.9:1 and unreadable.

Sensor instance colours are deliberately **outside** this palette. They are data, and twelve of
them have to stay tellable apart, which six brand colours cannot do. They are pastel, bounded by
constraints that `store/__tests__/sensorColors.test.ts` pins: every pair stays apart as a solid
and in the 0.75 wireframe, the faintest 0.30 fill stays visible against the viewport, each swatch
clears 2.2:1 on a white card, and none of them may read as the blind-sector shading — that last one
would turn an uncovered sector into apparent coverage.

Uncovered sectors shade **light grey** (`grey` at 0.42, landing near `#E0E0E0`), not red. A gap is
a finding, not a fault, and red read as an error the moment more than a sector or two was open.
Grey needs the higher opacity: at the 0.16 the red used it is invisible over the near-white ground.

## Sidebar, top to bottom

Each section is its own bordered card on the off-white background, with a tinted header — a
boundary you can see as a shape rather than a hairline between two runs of text.

1. **Vehicle** — length X, width Y, height Z, ground clearance, wheelbase. A Box / Rounded /
   Cylinder shape control, with a corner radius field that appears only for Rounded and warns when
   the figure exceeds half the shorter side. A Car / Van / Bus model control for the roofline,
   independent of the shape: shape is the plan outline, model is the side profile. A corner radius
   applies to every block of the body, not only the one at ground level. Toggles for the body
   itself, its wheels, and dimension lines; hiding the body leaves the sensors and their volumes on
   their own, and greys out the wheels toggle, which has nothing left to act on. Dimensions are
   drawn as an SVG overlay above the three
   orthographic panes — never in ISO, where extension lines read as clutter rather than measurement
   — using the same projection the panes do, so the annotation cannot drift from the drawing. Each
   dimension stands off the body, and pulls back inside the pane when a fitted view leaves no room
   rather than spilling into its neighbour.
2. **Grid** — the grid's own on/off, then cell size in metres, default 1. The grid holds its line
   count and changes
   how much ground it covers instead, so a fine cell costs no more to draw than a coarse one.
3. **Sensors** — the list, then *Add sensor*, *Duplicate*, *Export*, *Import*, *Reset*.
   *Reset* drops every sensor and refits the four views; it asks first, since there is no undo.
4. **Display** — checkboxes for shaded volume, wireframe edges, ground footprint, optical axis.
   Slider for FOV opacity, 5–70%, default 30%. The Off / Move / Rotate drag control lives here —
   `dragMode` is one global value, so it belongs with the other layout-wide switches rather than
   repeated under each sensor, where it was also out of reach whenever the list was collapsed.
5. **Coverage** — blind spot report for the current layout.
6. **Shortcuts** — a short key and mouse reference. Named for what it lists rather than for
   navigation alone: undo, delete and suppressing the snap to the body are in there too.

## Sensor list and editor

Each row: colour swatch, name, a compact `120°×40° 20m` summary, visibility toggle. Clicking a row
selects it and expands the editor inline.

Editor contents:

- **Model** — catalogue autocomplete (manufacturer + model). Selecting one fills HFOV, VFOV and
  range and marks them as inherited. A *Customise* action converts the instance to a custom spec so
  the fields become directly editable. Show the datasheet link when the spec has one, and show a
  warning chip when `verified` is false.
- **Name** and **colour**.
- **Position** — X forward, Y left, Z up. Step 0.01 m.
- **Orientation** — yaw (+ left), pitch (+ up), roll (+ CW). Step 1°.
- **Field of view** — HFOV, VFOV, range.
- **Readout** — footprint area, X extent, Y extent, blind gap, plus the inside-the-body warning
  when it applies.
- **Delete**.

Label every angle field with its sign convention in the label itself — `Yaw ° (+ left)`. Engineers
will get this wrong otherwise, and a wrong sign is invisible until the FOV points the wrong way.

## Viewports

Four `<View>` panes from `@react-three/drei` sharing one canvas.

| View | Camera | Looks from | Up | On screen |
|---|---|---|---|---|
| TOP | Orthographic | +Z | +X | nose up, vehicle right on screen right |
| FRONT | Orthographic | +X | +Z | looking aft, vehicle left on screen right |
| LEFT | Orthographic | +Y | +Z | left flank, nose points left |
| ISO | Perspective, fov 36° | orbital | +Z | free orbit |

Set `camera.up` before `lookAt`.

Label each pane with its name, its current scale (`24.0 m across` for orthographic, `d = 16.0 m`
for perspective) and an axis hint.

## Navigation

- **Scroll** — zoom.
- **Drag on empty space** — pan. Derive screen-right and screen-up from columns 0 and 1 of the
  camera's world matrix and scale by metres-per-pixel so the drag tracks the cursor exactly.
- **Drag in ISO** — orbit. Azimuth free, elevation clamped to ±83°. **Shift + drag** pans.
- **Double-click a pane** — fit that pane.
- **Keys** — `+`, `−`, `F` for fit. `Delete` removes the selected sensor while a drag mode is on,
  asking first until the engineer turns the prompt off. `Ctrl+Z` undoes and `Ctrl+Y` redoes, with
  `Ctrl+Shift+Z` as a second redo; `Cmd` stands in for `Ctrl` on macOS. Ignore keystrokes while a
  text field has focus — including the undo pair, so `Ctrl+Z` in a number field undoes the typing
  rather than the layout.

### Linked zoom

A switch labelled **Link zoom**, on by default. While on, scrolling in any pane multiplies the
zoom of all four panes by the same factor. While off, each pane zooms alone. Panning is always
per-pane.

### Fit all

Compute the bounding box of the vehicle plus every visible FOV volume, then frame it in each pane
— project the box corners onto that pane's screen-right and screen-up axes and correct for that
pane's own aspect ratio, so a long-range sensor is never clipped. Call it once on first layout.

Zoom controls appear in two places: a row in the sidebar and a floating group at the bottom right
of the viewport area, each with **−**, **Fit all**, **+**.

## Dragging a sensor

This is the feature that makes the tool worth using. Two independent mechanisms.

**In ISO — gizmo.** `<TransformControls>` attached to the selected sensor's marker. A segmented
control switches between *Move* and *Rotate*. On `objectChange`, write straight to
`updatePose`. Disable orbit while the gizmo is being dragged, or the camera will fight the drag.

**In TOP — direct 2D drag.** Press on a sensor marker and drag; map screen delta to world X and Y
through the orthographic scale. This is the mode people will actually use for the first pass,
because placing something on a plan view is natural and a 3D gizmo is not.

**Snap to body.** While dragging, raycast against the vehicle box. If the hit is within 0.15 m,
snap the sensor to the surface and align its optical axis to the outward face normal. Hold `Alt`
to suppress. This matches how sensors are really mounted and saves a lot of typing.

During a drag the FOV volume and ground polygon update every frame. The blind spot report does
not — it recomputes 150 ms after the drag ends.

## Copy

Plain, active, specific. `Add sensor`, not `Create new sensor entry`. `Fit all views`, not
`Reset camera`. When the layout has no sensors, the list says `No sensors yet — add one to
begin.`, which is an instruction rather than a mood.
